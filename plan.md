# Universal Statistician — исследование референсов и предложение по MVP

## Контекст

Цель проекта — универсальный статистический помощник, который отвечает на вопросы
о статистике за любой период, в любом формате, опираясь только на официальные
источники.

По ответам на уточняющие вопросы:
- **Интерфейс**: в целевом виде — всё сразу (MCP-сервер + чат + API/дашборд), но
  стартуем как **личный/локальный инструмент**, без публичной инфраструктуры.
- **Источники данных для MVP**: международные организации (SDMX-провайдеры).
- **Язык запросов**: многоязычный.
- **Аудитория на старте**: сам пользователь / небольшая команда, self-hosted.

Дополнительное требование к конечному продукту: система должна не только отдавать
сырые ряды из источников, но и **генерировать собственные производные ряды данных**
на их основе — в первую очередь сравнительные межстрановые и межиндикаторные таблицы
(например, "ВВП на душу населения по странам X, Y, Z за 2015–2024" или "инфляция vs
безработица по стране за период"). Это меняет границы MVP — см. раздел 4.

Ниже — анализ похожих open source проектов и предложение по стеку, архитектуре,
границам MVP и последовательности разработки.

### Общие выводы

**Что стоит повторить:**
1. Строить поверх `sdmx` (khaeru) вместо своего клиента — экономит месяцы работы и даёт сразу 7+ источников.
2. Один движок данных → несколько тонких интерфейсов (MCP / CLI / API), без дублирования логики (паттерн sdmx-dl, TAM-MCP-Server).
3. Обязательная атрибуция источника в каждом ответе (провайдер, код датасета, дата обращения, ссылка) — принцип из openecon-data, критичен из-за требования "только официальные источники".
4. Каталог/поиск индикаторов поверх сырых API — без этого "универсальность" не достигается (урок DataUSA).
5. Кэш начинать с локального (SQLite/diskcache), Redis — опционально, когда появится реальная многопользовательская нагрузка (паттерн TAM-MCP-Server).

**Чего избегать:**
1. Собственный NLU/LLM-парсер запросов (как в openecon-data) — дорого поддерживать одному разработчику; вместо этого MCP-инструменты остаются структурированными и детерминированными, а понимание языка отдаётся LLM-хосту (Claude и т.п.).
2. Мульти-языковый стек ради отдельных интерфейсов (Java+CLI+Web в sdmx-dl) — держать один язык (Python) везде.
3. Форк узких одноисточниковых MCP-серверов как основы — их архитектура не рассчитана на рост числа источников и каталог.
4. Избыточная инфраструктура на старте (Redis, микросервисы, auth) — не нужна для личного/локального инструмента.

## 2. Предлагаемый стек

- **Язык**: Python (единственный язык для всех слоёв — данные, MCP, CLI, будущий API).
- **Слой доступа к данным**: `sdmx` (khaeru) как основа коннектора к SDMX-источникам, обёрнутая в собственный `Provider`-интерфейс, чтобы позже добавлять не-SDMX источники (PX-Web, нацстатслужбы) без изменения верхних слоёв.
- **Каталог/индекс**: SQLite (+FTS5 для полнотекстового поиска по названиям индикаторов/датасетов на разных языках).
- **Кэш**: локальный, на базе SQLite/diskcache с TTL по источнику; Redis — не в MVP.
- **Интерфейс для MVP**: MCP-сервер (Python MCP SDK) — основной; тонкий CLI (Typer) — для разработки/отладки без MCP-клиента.
- **Понимание языка/многоязычность**: не встраиваем свой NLU — многоязычные запросы разбирает LLM-хост, подключённый через MCP; сервер получает уже структурированный вызов инструмента (индикатор/страна/период). Метаданные индикаторов хранятся в языках, которые отдают сами источники (SDMX обычно даёт multi-language labels "из коробки"), плюс английский как фолбэк.
- **Тесты/качество**: pytest, типизация (mypy опционально), структурное логирование.
- **Будущие слои (вне MVP)**: FastAPI (REST поверх того же ядра) → React-дашборд поверх FastAPI → отдельное чат-приложение, переиспользующее те же MCP-инструменты через Claude API function calling.

## 3. Архитектура (целевая, MVP — подмножество)

```
                    ┌───────────────────────────┐
                    │   Интерфейсы (тонкие)     │
                    │  MCP-сервер │ CLI │ (API)  │  ← добавляются поверх, без дублирования логики
                    └─────────────┬─────────────┘
                                  │
                    ┌─────────────▼─────────────┐
                    │      Core query engine     │  нормализация запроса → провайдер-запрос(ы) → нормализованный ответ + атрибуция
                    └──────┬───────────────┬─────┘
                            │
                    ┌───────▼───────────────────┐
                    │  Compose layer (derived)   │  собирает N вызовов провайдеров в
                    │  межстрановые/межиндикатор.│  одну таблицу: общая ось (страна×год),
                    │  таблицы, простые расчёты  │  сведение единиц, вычисляемые колонки
                    │  (ratio, growth, rank)     │  (доля, темп роста, ранг)
                    └──────┬───────────────┬─────┘
             ┌─────────────▼───┐   ┌───────▼────────────┐
             │ Catalog/Index    │   │  Cache (TTL)        │
             │ (SQLite FTS5)    │   │  (SQLite/diskcache)  │
             └─────────────┬───┘   └───────┬────────────┘
                            │               │
                    ┌───────▼───────────────▼───────┐
                    │   Provider interface           │
                    │  (get_series, search, meta)    │
                    └───────┬─────────────────────────┘
                            │
              ┌─────────────▼─────────────┐
              │  Generic SDMX provider     │  (обёртка над khaeru/sdmx)
              │  World Bank │ Eurostat │   │
              │  IMF │ OECD │ (+ ещё)      │
              └────────────────────────────┘
```

## 4. Границы MVP (v0.1)

**Входит:**
- Python-пакет, локальный запуск, без auth, без Docker-обязательности (Dockerfile — не критично).
- 3–4 источника через один generic SDMX provider: World Bank, Eurostat, IMF, OECD.
- Каталог индикаторов с полнотекстовым поиском (SQLite FTS5), построенный из метаданных источников.
- Получение временного ряда по индикатору + стране/региону + периоду, с нормализацией в единый формат (таблица + метаданные: источник, код датасета, дата обращения, ссылка на первоисточник).
- Локальный кэш с TTL.
- **Compose-слой**: сборка нескольких вызовов провайдера(ов) в одну производную таблицу —
  межстрановое сравнение одного индикатора (страна × год) и межиндикаторное сравнение
  для одной страны (индикатор × год), с приведением к общей оси периодов и явной пометкой
  источника для каждой ячейки/колонки (данные из разных источников не должны молча смешиваться
  без атрибуции). Простые вычисляемые колонки: доля/ratio, темп роста год-к-году, ранг.
- MCP-сервер с инструментами: `search_indicator`, `get_series`, `compare` (межстрановое/межиндикаторное сравнение), `list_sources`, `describe_source`.
- CLI-обёртка поверх того же ядра — для разработки и smoke-тестов без MCP-клиента.
- Базовые тесты на core query engine, compose-слой и на каждый provider.

**Не входит (следующие этапы):**
- Дашборд/фронтенд, отдельное standalone чат-приложение.
- Многопользовательский режим, аутентификация, Redis.
- Российские/национальные источники (Росстат, ЕМИСС) — отдельный не-SDMX коннектор.
- Собственная генерация графиков/визуализаций — форматирование ответа (текст/таблица/график) делегируется LLM-хосту на основе структурированных данных из compare/get_series.
- Сложная аналитика/прогнозирование (регрессии, ML, форecasting) поверх производных таблиц — только базовые расчёты (ratio, темп роста, ранг).

## 5. Последовательность разработки

1. Скелет репозитория + `Provider`-интерфейс + generic SDMX provider на **одном** источнике (World Bank) — сквозной путь от запроса до нормализованного ответа с атрибуцией. **✅ сделано**
2. Добавить Eurostat, IMF, OECD через тот же generic provider — проверить, что абстракция не течёт. **✅ сделано (Eurostat, IMF)**, OECD сознательно пропущен: в отличие от WB/IMF/Eurostat, для него нет проверенного примера рабочего запроса (ни в доках, ни в тест-сьюте `sdmx1`) — угадывать ключ рискованно, добавим при появлении сети или документированного примера. Проверка абстракции показала важный нюанс: запись в реестре — это "источник + датафлоу", а не "источник целиком" (см. `providers/registry.py` и README).
3. Каталог/индекс (SQLite FTS5) + инструмент поиска по индикаторам на нескольких языках. **✅ сделано.** Поиск вынесен из `Provider` в `QueryEngine`/`Catalog` — он межисточниковый по своей природе. Индекс пока заполнен только тремя уже проверенными индикаторами (по одному на источник); полное покрытие требует живого запроса к codelist/conceptscheme каждого источника (недоступно в этой песочнице).
4. Слой кэша (TTL, по источнику). **✅ сделано.** SQLite-кэш в `QueryEngine.get_series()`, ключ — полный запрос (источник+индикатор+регион+период), TTL задаётся в `SDMXSourceConfig.cache_ttl_seconds` (default 24ч) и прокидывается через `Provider.cache_ttl_seconds`. Redis не нужен — личный инструмент без многопользовательской нагрузки.
5. **Compose-слой**: сборка нескольких `get_series`-вызовов в межстрановую и межиндикаторную таблицу с общей осью периодов, атрибуцией по колонке/ячейке и базовыми вычисляемыми колонками (ratio, темп роста, ранг). **✅ сделано** (`core/compose.py`): `compare_across_countries`/`compare_across_indicators` строят таблицу, `with_growth`/`with_ratio`/`with_rank` добавляют вычисляемые колонки поверх базовых; вычисляемые колонки помечены `derived=True` и без `Attribution` (не из источника), базовые сохраняют атрибуцию своего `get_series()`-вызова.
6. MCP-сервер поверх ядра (`search_indicator`, `get_series`, `compare`, `list_sources`, `describe_source`) — сквозной тест с Claude Desktop/Code. **✅ сделано** (`mcp_server.py`, тонкая обёртка над новым `tools.py`, запуск через `universal-statistician-mcp`). Сквозной тест через `server.call_tool()` (не просто `tools.py` напрямую) вскрыл реальный баг: MCP-сервер выполняет tool-вызовы в worker-потоке, `sqlite3`-соединения `Catalog`/`Cache` по умолчанию это отклоняют — исправлено (`check_same_thread=False` + `threading.Lock`, с regression-тестами).
7. CLI поверх того же ядра. **✅ сделано** (`cli.py`, Typer, тонкая обёртка над `tools.py`, запуск через `ustat`). Некорректный ввод (неизвестный источник, неполный `compare`) даёт понятное сообщение в stderr + код выхода 1 вместо traceback.
8. Документация (README, таблица покрытия источников) + базовые тесты. **✅ сделано.** README переписан в справочную структуру (архитектура → покрытие источников → установка → запуск → тесты → roadmap) вместо хронологии по коммитам. Добавлен `test_mcp_server.py`, тестирующий реальный `server.call_tool()` (не только `tools.py`), а не только точечные unit-тесты — это единственный способ, которым нашёлся баг с потоками на шаге 6. **64 офлайн-теста, MVP (шаги 1–8) завершён.**
9. *(после MVP)* FastAPI REST-слой поверх ядра → дашборд → нацстат-коннекторы (Росстат/ЕМИСС) → отдельное чат-приложение → более сложная аналитика (прогнозирование, регрессии) поверх compose-слоя.
   - 9a. **FastAPI REST-слой.** **✅ сделано** (`api.py`, третий тонкий интерфейс над `tools.py`, запуск `uvicorn universal_statistician.api:app`). `GET /sources`, `GET /sources/{id}`, `GET /search`, `GET /series`, `POST /compare`; `UnknownSourceError` → 404, `ValueError` → 400 (тот же принцип, что в CLI). Проверено `TestClient` (`test_api.py`) и вручную живым `uvicorn` + `curl`. Тот же класс риска, что нашёлся в MCP-сервере (Starlette тоже гоняет синхронные хендлеры в worker-потоке), прошёл без правок — фикс `check_same_thread=False`+`Lock` был общим для `Catalog`/`Cache`, а не специфичным для MCP. **71 офлайн-тест.**
   - 9b–9d (следующие раунды): веб-дашборд поверх FastAPI → нацстат-коннекторы (Росстат/ЕМИСС) → отдельное чат-приложение → аналитика поверх compose-слоя.
