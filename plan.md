# Universal Statistician — исследование референсов и предложение по MVP

## Контекст

Цель проекта — универсальный статистический помощник, который отвечает на вопросы
о статистике за любой период, в любом формате, опираясь только на официальные
источники.

По ответам на уточняющие вопросы:
- **Интерфейс**: в целевом виде — всё сразу (MCP-сервер + чат + API/дашборд), но
  стартуем как **личный/локальный инструмент**, без публичной инфраструктуры.
- **Источники данных для MVP**: международные организации (SDMX-провайдеры).
- **Язык запросов**: многоязычный.
- **Аудитория на старте**: сам пользователь / небольшая команда, self-hosted.

Дополнительное требование к конечному продукту: система должна не только отдавать
сырые ряды из источников, но и **генерировать собственные производные ряды данных**
на их основе — в первую очередь сравнительные межстрановые и межиндикаторные таблицы
(например, "ВВП на душу населения по странам X, Y, Z за 2015–2024" или "инфляция vs
безработица по стране за период"). Это меняет границы MVP — см. раздел 4.

Ниже — анализ похожих open source проектов и предложение по стеку, архитектуре,
границам MVP и последовательности разработки.

### Общие выводы

**Что стоит повторить:**
1. Строить поверх `sdmx` (khaeru) вместо своего клиента — экономит месяцы работы и даёт сразу 7+ источников.
2. Один движок данных → несколько тонких интерфейсов (MCP / CLI / API), без дублирования логики (паттерн sdmx-dl, TAM-MCP-Server).
3. Обязательная атрибуция источника в каждом ответе (провайдер, код датасета, дата обращения, ссылка) — принцип из openecon-data, критичен из-за требования "только официальные источники".
4. Каталог/поиск индикаторов поверх сырых API — без этого "универсальность" не достигается (урок DataUSA).
5. Кэш начинать с локального (SQLite/diskcache), Redis — опционально, когда появится реальная многопользовательская нагрузка (паттерн TAM-MCP-Server).

**Чего избегать:**
1. Собственный NLU/LLM-парсер запросов (как в openecon-data) — дорого поддерживать одному разработчику; вместо этого MCP-инструменты остаются структурированными и детерминированными, а понимание языка отдаётся LLM-хосту (Claude и т.п.).
2. Мульти-языковый стек ради отдельных интерфейсов (Java+CLI+Web в sdmx-dl) — держать один язык (Python) везде.
3. Форк узких одноисточниковых MCP-серверов как основы — их архитектура не рассчитана на рост числа источников и каталог.
4. Избыточная инфраструктура на старте (Redis, микросервисы, auth) — не нужна для личного/локального инструмента.

## 2. Предлагаемый стек

- **Язык**: Python (единственный язык для всех слоёв — данные, MCP, CLI, будущий API).
- **Слой доступа к данным**: `sdmx` (khaeru) как основа коннектора к SDMX-источникам, обёрнутая в собственный `Provider`-интерфейс, чтобы позже добавлять не-SDMX источники (PX-Web, нацстатслужбы) без изменения верхних слоёв.
- **Каталог/индекс**: SQLite (+FTS5 для полнотекстового поиска по названиям индикаторов/датасетов на разных языках).
- **Кэш**: локальный, на базе SQLite/diskcache с TTL по источнику; Redis — не в MVP.
- **Интерфейс для MVP**: MCP-сервер (Python MCP SDK) — основной; тонкий CLI (Typer) — для разработки/отладки без MCP-клиента.
- **Понимание языка/многоязычность**: не встраиваем свой NLU — многоязычные запросы разбирает LLM-хост, подключённый через MCP; сервер получает уже структурированный вызов инструмента (индикатор/страна/период). Метаданные индикаторов хранятся в языках, которые отдают сами источники (SDMX обычно даёт multi-language labels "из коробки"), плюс английский как фолбэк.
- **Тесты/качество**: pytest, типизация (mypy опционально), структурное логирование.
- **Будущие слои (вне MVP)**: FastAPI (REST поверх того же ядра) → React-дашборд поверх FastAPI → отдельное чат-приложение, переиспользующее те же MCP-инструменты через Claude API function calling.

## 3. Архитектура (целевая, MVP — подмножество)

```
                    ┌───────────────────────────┐
                    │   Интерфейсы (тонкие)     │
                    │  MCP-сервер │ CLI │ (API)  │  ← добавляются поверх, без дублирования логики
                    └─────────────┬─────────────┘
                                  │
                    ┌─────────────▼─────────────┐
                    │      Core query engine     │  нормализация запроса → провайдер-запрос(ы) → нормализованный ответ + атрибуция
                    └──────┬───────────────┬─────┘
                            │
                    ┌───────▼───────────────────┐
                    │  Compose layer (derived)   │  собирает N вызовов провайдеров в
                    │  межстрановые/межиндикатор.│  одну таблицу: общая ось (страна×год),
                    │  таблицы, простые расчёты  │  сведение единиц, вычисляемые колонки
                    │  (ratio, growth, rank)     │  (доля, темп роста, ранг)
                    └──────┬───────────────┬─────┘
             ┌─────────────▼───┐   ┌───────▼────────────┐
             │ Catalog/Index    │   │  Cache (TTL)        │
             │ (SQLite FTS5)    │   │  (SQLite/diskcache)  │
             └─────────────┬───┘   └───────┬────────────┘
                            │               │
                    ┌───────▼───────────────▼───────┐
                    │   Provider interface           │
                    │  (get_series, search, meta)    │
                    └───────┬─────────────────────────┘
                            │
              ┌─────────────▼─────────────┐
              │  Generic SDMX provider     │  (обёртка над khaeru/sdmx)
              │  World Bank │ Eurostat │   │
              │  IMF │ OECD │ (+ ещё)      │
              └────────────────────────────┘
```

## 4. Границы MVP (v0.1)

**Входит:**
- Python-пакет, локальный запуск, без auth, без Docker-обязательности (Dockerfile — не критично).
- 3–4 источника через один generic SDMX provider: World Bank, Eurostat, IMF, OECD.
- Каталог индикаторов с полнотекстовым поиском (SQLite FTS5), построенный из метаданных источников.
- Получение временного ряда по индикатору + стране/региону + периоду, с нормализацией в единый формат (таблица + метаданные: источник, код датасета, дата обращения, ссылка на первоисточник).
- Локальный кэш с TTL.
- **Compose-слой**: сборка нескольких вызовов провайдера(ов) в одну производную таблицу —
  межстрановое сравнение одного индикатора (страна × год) и межиндикаторное сравнение
  для одной страны (индикатор × год), с приведением к общей оси периодов и явной пометкой
  источника для каждой ячейки/колонки (данные из разных источников не должны молча смешиваться
  без атрибуции). Простые вычисляемые колонки: доля/ratio, темп роста год-к-году, ранг.
- MCP-сервер с инструментами: `search_indicator`, `get_series`, `compare` (межстрановое/межиндикаторное сравнение), `list_sources`, `describe_source`.
- CLI-обёртка поверх того же ядра — для разработки и smoke-тестов без MCP-клиента.
- Базовые тесты на core query engine, compose-слой и на каждый provider.

**Не входит (следующие этапы):**
- Дашборд/фронтенд, отдельное standalone чат-приложение.
- Многопользовательский режим, аутентификация, Redis.
- Российские/национальные источники (Росстат, ЕМИСС) — отдельный не-SDMX коннектор.
- Собственная генерация графиков/визуализаций — форматирование ответа (текст/таблица/график) делегируется LLM-хосту на основе структурированных данных из compare/get_series.
- Сложная аналитика/прогнозирование (регрессии, ML, форecasting) поверх производных таблиц — только базовые расчёты (ratio, темп роста, ранг).

## 5. Последовательность разработки

1. Скелет репозитория + `Provider`-интерфейс + generic SDMX provider на **одном** источнике (World Bank) — сквозной путь от запроса до нормализованного ответа с атрибуцией. **✅ сделано**
2. Добавить Eurostat, IMF, OECD через тот же generic provider — проверить, что абстракция не течёт. **✅ сделано (Eurostat, IMF)**, OECD сознательно пропущен: в отличие от WB/IMF/Eurostat, для него нет проверенного примера рабочего запроса (ни в доках, ни в тест-сьюте `sdmx1`) — угадывать ключ рискованно, добавим при появлении сети или документированного примера. Проверка абстракции показала важный нюанс: запись в реестре — это "источник + датафлоу", а не "источник целиком" (см. `providers/registry.py` и README).
3. Каталог/индекс (SQLite FTS5) + инструмент поиска по индикаторам на нескольких языках. **✅ сделано.** Поиск вынесен из `Provider` в `QueryEngine`/`Catalog` — он межисточниковый по своей природе. Индекс пока заполнен только тремя уже проверенными индикаторами (по одному на источник); полное покрытие требует живого запроса к codelist/conceptscheme каждого источника (недоступно в этой песочнице).
4. Слой кэша (TTL, по источнику). **✅ сделано.** SQLite-кэш в `QueryEngine.get_series()`, ключ — полный запрос (источник+индикатор+регион+период), TTL задаётся в `SDMXSourceConfig.cache_ttl_seconds` (default 24ч) и прокидывается через `Provider.cache_ttl_seconds`. Redis не нужен — личный инструмент без многопользовательской нагрузки.
5. **Compose-слой**: сборка нескольких `get_series`-вызовов в межстрановую и межиндикаторную таблицу с общей осью периодов, атрибуцией по колонке/ячейке и базовыми вычисляемыми колонками (ratio, темп роста, ранг). **✅ сделано** (`core/compose.py`): `compare_across_countries`/`compare_across_indicators` строят таблицу, `with_growth`/`with_ratio`/`with_rank` добавляют вычисляемые колонки поверх базовых; вычисляемые колонки помечены `derived=True` и без `Attribution` (не из источника), базовые сохраняют атрибуцию своего `get_series()`-вызова.
6. MCP-сервер поверх ядра (`search_indicator`, `get_series`, `compare`, `list_sources`, `describe_source`) — сквозной тест с Claude Desktop/Code. **✅ сделано** (`mcp_server.py`, тонкая обёртка над новым `tools.py`, запуск через `universal-statistician-mcp`). Сквозной тест через `server.call_tool()` (не просто `tools.py` напрямую) вскрыл реальный баг: MCP-сервер выполняет tool-вызовы в worker-потоке, `sqlite3`-соединения `Catalog`/`Cache` по умолчанию это отклоняют — исправлено (`check_same_thread=False` + `threading.Lock`, с regression-тестами).
7. CLI поверх того же ядра. **✅ сделано** (`cli.py`, Typer, тонкая обёртка над `tools.py`, запуск через `ustat`). Некорректный ввод (неизвестный источник, неполный `compare`) даёт понятное сообщение в stderr + код выхода 1 вместо traceback.
8. Документация (README, таблица покрытия источников) + базовые тесты. **✅ сделано.** README переписан в справочную структуру (архитектура → покрытие источников → установка → запуск → тесты → roadmap) вместо хронологии по коммитам. Добавлен `test_mcp_server.py`, тестирующий реальный `server.call_tool()` (не только `tools.py`), а не только точечные unit-тесты — это единственный способ, которым нашёлся баг с потоками на шаге 6. **64 офлайн-теста, MVP (шаги 1–8) завершён.**
9. *(после MVP)* FastAPI REST-слой поверх ядра → дашборд → нацстат-коннекторы (Росстат/ЕМИСС) → отдельное чат-приложение → более сложная аналитика (прогнозирование, регрессии) поверх compose-слоя.
   - 9a. **FastAPI REST-слой.** **✅ сделано** (`api.py`, третий тонкий интерфейс над `tools.py`, запуск `uvicorn universal_statistician.api:app`). `GET /sources`, `GET /sources/{id}`, `GET /search`, `GET /series`, `POST /compare`; `UnknownSourceError` → 404, `ValueError` → 400 (тот же принцип, что в CLI). Проверено `TestClient` (`test_api.py`) и вручную живым `uvicorn` + `curl`. Тот же класс риска, что нашёлся в MCP-сервере (Starlette тоже гоняет синхронные хендлеры в worker-потоке), прошёл без правок — фикс `check_same_thread=False`+`Lock` был общим для `Catalog`/`Cache`, а не специфичным для MCP. **71 офлайн-тест.**
   - 9b. **Веб-дашборд поверх FastAPI.** **✅ сделано.** React + Vite + TypeScript в `frontend/`, три вкладки (Поиск/Ряд/Сравнение), линейный график через `recharts` (по решению пользователя — не только таблицы). `CORSMiddleware` в `api.py` под любой локальный origin.

     Живая проверка в браузере (Playwright/Chromium, не `TestClient`) нашла два реальных бага, которые юнит-тесты пропустили:
     1. **Необработанное исключение провайдера ломает CORS.** При сетевом сбое (`api.worldbank.org` заблокирован в песочнице) необработанное исключение из `get_series`/`compare` не долетало до `CORSMiddleware` нормально — браузер репортил "blocked by CORS policy" вместо реальной причины. Исправлено: `_call()` в `api.py` теперь ловит `Exception` целиком → `HTTPException(502, ...)`, закреплено `test_provider_failure_is_a_clean_502_with_cors_headers`.
     2. **Невидимый текст на вкладках.** Глобальное `button { color: white }` протекало в `.tabs button`, где фон сбрасывался в `none` — белый текст на белом фоне. Исправлено `color: inherit` в `.tabs button`. Нашлось только по скриншоту, не по логике/типам.

     Отдельного JS-тест-фреймворка нет — только ручная проверка вживую (Поиск — полностью реальными данными, сеть не нужна; Ряд/Сравнение — что форма отправляется и ошибка показывается понятным баннером, не белым экраном), соответствует объёму проверки личного инструмента. **72 офлайн-теста (Python-часть).**
   - 9c. **Нацстат-коннектор (не-SDMX провайдер).** Изначально в плане — Росстат/ЕМИСС; по факту не добавлен, вместо него — Statistics Sweden (SCB) через стандарт PX-Web (второй стандарт из исходного research, помимо SDMX). Причины и результат:
     - `fedstat.ru` (ЕМИСС) сам по себе заблокирован egress-политикой песочницы (проверено — заблокирован вообще любой внешний хост, кроме pypi/npm/github/anthropic, не только этот), и у него нет документированного API — только скрейпинг HTML/JS внутренней страницы индикатора, который единственная найденная референсная реализация (`fedstatAPIr`, R) сама описывает как "эмпирически определённый 12-й `<script>`-тег". Без единого источника правды (в отличие от SDMX, где был тест-сьют `sdmx1`) угадывать эту логику — риск получить незаметно сломанный или тихо неверный коннектор. Отложено по тому же принципу, что и OECD.
     - Вместо этого: `PXWebProvider` (`providers/pxweb_provider.py` + `pxweb_registry.py`) поверх `pxwebpy` — активно поддерживаемого, протестированного Python-клиента PX-Web API (используется SCB, Норвегией, Финляндией), тем же принципом, что и `sdmx1` для SDMX ("не писать свой клиент"). Источник: `SCB_TAB6471`, значения проверены по собственному тест-сьюту `pxwebpy` (`test_get_table_data_coerce_to_list`). Никаких изменений в `Provider`, `QueryEngine`, `Catalog`, `Cache`, `compose.py`, `tools.py` или любом интерфейсе не потребовалось — это и есть архитектурное доказательство, ради которого исходно был предложен этот шаг.
     - По пути нашёлся и исправлен ещё один реальный баг того же класса, что threading/CORS: `PxApi(...)` (в отличие от ленивого `sdmx.Client()`) делает сетевой запрос прямо в конструкторе. Наивная обёртка сломала бы старт `default_engine()` — вызывается при старте каждого интерфейса — если SCB недоступен, даже для пользователей, которым нужен только WB_WDI. Исправлено до того, как стало багом: `PXWebProvider` строит `PxApi` лениво при первом `get_series()`. Закреплено `test_construction_does_not_touch_the_network`.
     - Офлайн-тесты для `PXWebProvider` построены тем же принципом, что для SDMX: реальная функция `pxweb._internal.functions.unpack_table_data`, скормленная сконструированному JSON-stat2, а не выдуманная форма ответа. **77 офлайн-тестов.**
   - 9d. **Отдельное чат-приложение.** **✅ сделано.** CLI (`ustat chat`, подтверждено пользователем — не вкладка в дашборде, чтобы не заводить хранение состояния диалога на бэкенде ради одного раунда). `chat.py`: схемы инструментов и их выполнение переиспользованы напрямую от `mcp_server.server` (`list_tools()`/`call_tool()`), а не описаны/продублированы заново — тот же принцип "определить один раз", что и `tools.py`, продолженный на схемы, не только логику. `ChatSession` — чистый, тестируемый цикл (tool_use → call_tool → tool_result → повтор, пока не придёт финальный текст), принимает клиент как параметр — фейковый в тестах, `anthropic.Anthropic()` в `run_chat()`.

     Офлайн-тест поймал реальный баг до первого живого запуска: `execute_tool_call` писал `_mcp_server.server.call_tool(...)`, хотя `_mcp_server` (`from mcp_server import server as _mcp_server`) — уже сам объект `MCPServer`, лишний `.server` уронил бы каждый вызов инструмента. Исправлено, закреплено.

     В этой песочнице нет `ANTHROPIC_API_KEY` — живой диалог с Claude не проверялся ни разу, это открыто зафиксировано (README, а не молчаливое допущение). Что проверено офлайн: конвертация MCP-схем → формат Claude API (реальные схемы от `mcp_server.server`), выполнение вызовов через настоящий `call_tool` для сетенезависимых инструментов, и цикл `ChatSession` на фейковом клиенте, собранном из настоящих `anthropic.types.Message`/`TextBlock`/`ToolUseBlock`/`Usage` — реальные типы SDK (проверено конструированием), не угаданная форма ответа. **85 офлайн-тестов.**

**Пункты 1–9d исходного плана выполнены.** Остаётся последний пункт из раздела 2 («Будущие слои») — более сложная аналитика (прогнозирование, регрессии) поверх compose-слоя — не запрошен явно, оставлен на будущее по необходимости.

## 7. Оценка по UOSA-Bench v1.0 (внешний бенчмарк)

Пользователь прислал внешний бенчмарк для статистических AI-ассистентов
(1000 баллов, 12 блоков A–L, 7 gate-критериев, adversarial suite, golden
derivation suite) и попросил проверить продукт по нему.

**✅ Сделано.** Полная оценка — [`docs/benchmarks/uosa-bench-v1-assessment.md`](./docs/benchmarks/uosa-bench-v1-assessment.md).
Дословное исполнение бенчмарка невозможно в этой среде (сеть заблокирована,
нет `ANTHROPIC_API_KEY`, каталог — 4 индикатора вместо 20 стран × 15
тематик) — вместо выдуманных баллов документ даёт честную классификацию
блоков/gate по реальному коду (с точными ссылками на файлы/строки) и то,
что реально прогнано офлайн (весь pytest-сьют, 85 тестов, плюс точечные
smoke-запросы через `ustat`/`tools.py`, включая реальный JSON-вывод
`compare()` с `growth`/`rank`/`ratio_to`).

Ключевые находки:
- **GATE-01 (fabricated data), GATE-02 (false attribution), GATE-06 (hidden
  estimation) — пройдены по конструкции кода**, не по обещанию промпта:
  подтверждено `grep`-проверкой (0 путей интерполяции/оценки во всём `src/`)
  и структурой `Provider`/`Attribution` (нет пути вернуть значение не из
  зарегистрированного источника).
- **GATE-05 (silent methodology break) не может быть подтверждён как
  пройденный** — механизма обнаружения разрывов методологии нет вообще. По
  правилу бенчмарка "любой gate fail = FAIL" это даёт формальный вердикт
  FAIL, несмотря на то, что три самых опасных gate проходятся уверенно.
- Целый блок G (revisions/vintage-awareness/конфликты источников) — 0 из 9
  пунктов реализовано или содержательно проверяемо; самый слабый блок
  продукта.
- В provenance (`core/models.py`) нет полей `unit`, `formula`,
  `input_series`, явной `status`-таксономии (Official/Derived/Composite/
  User-defined/Estimated) — Derived Data Trust Score оценён на ~65-70/100
  вместо требуемых ≥95.
- Из 20 операций Golden Derivation Suite — 3 реализованы полностью
  (share/ratio, growth, rank), 2 достижимы окольным путём (per capita/per
  employee через `with_ratio`), 15 отсутствуют (CAGR, moving average,
  rolling sum, currency conversion, index rebasing, real/nominal conversion
  и др.).
- Найден нюанс в уже существующем `with_growth`: функция всегда называется
  "YoY growth %", но реально считает период-к-периоду — для месячных рядов
  это будет MoM, посчитанный верно, но названный неверно.

Итоговая классификация — не выше нижней границы "Consumer-grade Assistant"
(700), вероятно ниже, прежде всего из-за отсутствующего блока G. Документ
заканчивается приоритизированным списком дешёвых улучшений в рамках уже
существующей архитектуры (в первую очередь — `unit`/`formula`/`input_series`
в provenance и явная `status`-таксономия), которые дадут наибольший эффект
на результат бенчмарка за наименьшую цену.

## 8. От MVP к универсальной платформе (расширение источников + NL-статистик)

Пользователь поставил новое, значительно более широкое ТЗ: расширить
покрытие источников на десятки/сотни индикаторов (World Bank, IMF, Eurostat,
OECD, нацстатслужбы) через discovery вместо ручного seed, и построить
естественноязыковой слой поверх ядра (query planner, вычисления с валидацией,
полный provenance для derived-статистик, `/ask`, NL-интерфейс в дашборде) —
без переписывания текущей архитектуры. Явное требование пользователя: не
одним огромным коммитом, а по фазам (13 штук), с тестами и документацией
после каждой. Полная разбивка по фазам, целевая архитектура и текущий статус
— в отдельном документе
[`docs/architecture/nl-platform.md`](./docs/architecture/nl-platform.md)
(живой, обновляется после каждой фазы) — не дублируется здесь, чтобы не
разъезжаться в двух местах.

### Фаза 1 — готово

Каталог метаданных: `IndicatorMeta`/`IndicatorEntry` расширены (обратно
совместимо) полями `unit`/`frequency`/`dataset_id`/`geographic_coverage`/
`dimensions`/`source_organization`/`official_url`/`last_updated`/`keywords`;
`Catalog` теперь честный upsert по `(source_id, indicator_id)` (было —
только вставка); новая опциональная способность провайдера —
`MetadataDiscoverable.discover_catalog_entries()`; новый `core/ingestion.py`
(discover → нормализация → каталог, `IngestionReport` с added/updated/
unchanged/errors); `QueryEngine.refresh_catalog()`/`catalog_stats()`; CLI —
`ustat catalog refresh [SOURCE_ID]` / `ustat catalog stats`. Ни один
реальный источник ещё не реализует discovery (это Фазы 2-6) — команда
честно репортит `"does not support metadata discovery"` вместо тихого
no-op. Пайплайн доказан офлайн через фейковый провайдер
(`tests/test_ingestion.py`), тем же принципом "доказать без сети", что уже
применялся для SDMX/PX-Web. **101 офлайн-тест** (было 85), полная
обратная совместимость подтверждена — ни один существующий тест не
переписан по смыслу, только один обновлён под расширенную (но
непротиворечивую) форму `as_dict()`.

### Фаза 2 — готово

`WorldBankProvider(SDMXProvider)` (`providers/worldbank_provider.py`)
добавляет `discover_catalog_entries()`, не трогая `get_series()`/`describe()`.
Discovery идёт через **другой** официальный API World Bank, не через SDMX:
бесспорный REST-эндпоинт `GET /v2/source/2/indicator` (source id 2 = WDI),
задокументированный самим World Bank
(`providers/worldbank_discovery.py`) — потому что в тест-сьюте `sdmx1` нет
проверенного примера SDMX-structure-запроса (codelist/dataflow) для этого
источника, только для `data`, и гадать здесь — та же ошибка, которую проект
уже отказался делать для OECD. `MetadataDiscoverable` — структурный
`Protocol`: `isinstance()`-проверка подтверждена на реальных объектах —
`WorldBankProvider` его удовлетворяет, обычный `SDMXProvider` (IMF/Eurostat)
— нет, хотя оба — один базовый класс.

Честная оговорка, как и для всех предыдущих источников: форма ответа v2 API
взята из официальной документации World Bank, но не проверена живым вызовом
в этой песочнице (сеть заблокирована) — парсинг и пагинация протестированы
офлайн (реальная документированная форма payload + фейковая сессия для
пагинации), один `network`-тест оставлен для машины с доступом в интернет.
Живая попытка `ustat catalog refresh WB_WDI` из песочницы подтвердила: URL
правильный (`/v2/source/2/indicator`), сетевой сбой обрабатывается чисто
(структурированная ошибка в `IngestionReport`, не падение) — реальное
доказательство корректности связки без доступа к самому ответу.

**110 офлайн-тестов** (было 101). `requests` добавлен как прямая (была
транзитивная через `sdmx1`) зависимость в `pyproject.toml`.

### Фаза 3 — готово

`IMFProvider(SDMXProvider)` (`providers/imf_provider.py`) добавляет
`discover_catalog_entries()` через настоящий SDMX structure-запрос
(`client.get("datastructure", resource_id="DSD_CPI")`) — в отличие от World
Bank, для IMF в тест-сьюте `sdmx1` ЕСТЬ проверенный пример
(`TestIMF_DATA.endpoint_args`: `"structure": dict(resource_id="DSD_CPI")`,
`"codelist": dict(resource_id="CL_COUNTRY")`), так что здесь не пришлось
уходить на отдельный REST API, как для WB. Ключевой архитектурный приём:
вместо того чтобы гадать, какое измерение DSD — "индикаторное", discovery
переиспользует ту же самую верифицированную позицию из
`key_dimensions` (`"{indicator}"`/`"{ref_area}"`), которая уже используется
для `get_series()` — один проверенный факт, а не два независимо угаданных;
несовпадение числа измерений даёт явную `IMFDiscoveryError`, а не тихий
неверный маппинг. `SDMXSourceConfig` получил поля `registry_id` (ключ в
`SOURCES`, нужен потому что `IndicatorEntry.source_id` должен быть именно
им — `"IMF_DATA_CPI"`, а не `config.source_id` `"IMF_DATA"`, который также
используется в `Attribution.source_id`, — асимметрия, которая существовала
и раньше, но не была явной) и `structure_id`.

Тесты — на реальных объектах `sdmx.model.v21`
(`DataStructureDefinition`/`Dimension`/`Codelist`/`Item`), включая кейс
несовпадения числа измерений. Живой прогон `ustat catalog refresh
IMF_DATA_CPI` из песочницы подтвердил точный URL
(`.../datastructure/all/DSD_CPI/latest?references=all` — `references=all`
подставился сам, дефолт самой библиотеки `sdmx1`, не угаданный параметр) и
чистую обработку сетевого сбоя. **117 офлайн-тестов** (было 110).

### Фаза 4 — готово

`EurostatProvider(SDMXProvider)` (`providers/eurostat_provider.py`) идёт по
пути, который сам `sdmx1` использует в своём тест-сьюте
(`TestESTAT.test_ss_data` — тот же тест, на который уже ссылался
`registry.py` за форматом ключа): `dataflow(resource_id=...).dataflow[...]
.structure`, и если `dsd.is_external_reference` — второй запрос
`client.get(resource=dsd)` на резолв. Комментарий в самом тесте объясняет
почему: "Even with ?references=all, ESTAT returns a short message with the
DSD as an external reference" — реальная, задокументированная в тест-сьюте
особенность именно ESTAT (в отличие от IMF, где один structure-запрос
резолвится сразу).

Логика "DSD → список `IndicatorEntry`" вынесена в общий
`providers/sdmx_discovery.py::entries_from_dsd()` — переиспользуется и
`IMFProvider`, и `EurostatProvider` (тот же приём с позицией
`{indicator}`/`{ref_area}` в `key_dimensions`, теперь не продублирован, а
факторизован). `IMFDiscoveryError` стал алиасом на общий
`SDMXDiscoveryError` для обратной совместимости.

Тесты — фейковый клиент, воспроизводящий реальную двухшаговую
external-reference-then-resolve последовательность на настоящих объектах
`sdmx.model.v21`, плюс кейс однократного резолва (подтверждает, что второй
запрос корректно пропускается, когда не нужен). Живой прогон `ustat catalog
refresh ESTAT_NAMA_10_GDP` подтвердил точный URL первого запроса
(`.../dataflow/ESTAT/NAMA_10_GDP/latest?references=descendants`, опять
дефолт самой библиотеки) и чистую обработку сетевого сбоя. **121 офлайн-тест**
(было 117).

### Фаза 5 — расследовано, осознанно не интегрировано

OECD переисследован по тому же стандарту verified-ground-truth, что и
остальные источники. **Первый черновик содержал ошибку**, которую поймал
собственный регрессионный тест
(`test_oecd_is_not_registered_pending_a_verified_discovery_example`) —
исправлено явно, а не тихо: изначально написал, что `sdmx1` декларирует
`structure: false` для ВСЕХ структурных эндпоинтов OECD, опираясь на
`sdmx.Client("OECD_JSON").source.supports`. На самом деле для источника
`"OECD"` (не `"OECD_JSON"`) `datastructure`/`dataflow`/`codelist`/
`conceptscheme` заявлены ПОДДЕРЖИВАЕМЫМИ — `False` только у отдельного,
менее используемого комбинированного эндпоинта `structure` (не того
`datastructure`, что нужен `entries_from_dsd()`).

Реальная, более узкая причина не регистрировать OECD: в тест-сьюте `sdmx1`
есть ровно один реальный, проверенный вживую запрос для OECD —
`data`, `resource_id="DSD_MSTI@DF_MSTI"`, БЕЗ ключа (весь датафлоу целиком),
и ни одного примера с конкретным `resource_id` для `datastructure`/
`dataflow`/`codelist` — в отличие от IMF (`DSD_CPI`) и Eurostat
(`NAMA_10_GDP`), скопировать неоткуда. Угадать `resource_id` по composite-id
`"DSD_MSTI@DF_MSTI"` (формат `@` не подтверждён) — именно та догадка,
которую проект принципиально не публикует. Единственный источник с
проверенным ПРИМЕРОМ С КЛЮЧОМ — `OECD_JSON` — требует небезопасного
даунгрейда SSL/TLS (задокументировано самими мейнтейнерами `sdmx1` как
отключение защиты от MITM).

Архитектура не меняется — как только появится проверенный пример
structure-запроса по актуальному `sdmx.oecd.org` API, `OECDProvider`
добавится тем же путём (`SDMXSourceConfig` + `entries_from_dsd()`), что
IMF/Eurostat. Полная запись — в `providers/registry.py` и
`docs/architecture/nl-platform.md`. Новый тест
`test_oecd_is_not_registered_pending_a_verified_discovery_example`
фиксирует находку и переоценит её сам, если `sdmx1` когда-нибудь изменит
эти флаги. **122 офлайн-теста** (было 121; код не менялся, кроме
докстрингов и одного нового регрессионного теста).

### Фаза 6 — готово

Два разных по природе шага. **(1)** PX-Web discovery обобщён на уровне
`PXWebProvider` целиком (не per-agency подкласс, как для SDMX): у PX-Web,
в отличие от SDMX, `get_table_variables()` идентичен для любого агентства
на протоколе — уже используется `get_series()` для метки временного
измерения, discovery просто читает ещё одно поле (`category.label`) из
той же, уже проверенной формы ответа (прочитано прямо из реализации
`pxweb/api.py`, не угадано). SCB теперь дискаверится по-настоящему, вместо
единственной вручную зашитой записи `000007SF`. Вторую PX-Web-службу
(Норвегия, `ssb` — реальный, известный библиотеке шорткат) НЕ
зарегистрировал: нет проверенного `table_id`, как был для SCB (`TAB6471`,
из тест-сьюта `pxwebpy`) — угадывать не стал.

**(2)** `CensusProvider` (`providers/census_provider.py`) — третий,
принципиально другой протокол: обычный REST/JSON API US Census Bureau, не
SDMX и не PX-Web/JSON-stat. Два реальных протокольных отличия обработаны
явно: один HTTP-запрос на год (Census публикует один датасет на год, не
диапазон периодов в одном запросе — `get_series()` требует оба периода,
иначе `ValueError`), и год без данных — это 404, пропускается явно, а не
падает весь многолетний запрос. Область — ACS 1-Year Estimates, коды
переменных вида `B01003_001E` стабильны от версии к версии уже больше
десяти лет (в отличие от Population Estimates Program, чьи имена переменных
менялись — сознательно не взял их).

**Честная оговорка**: в отличие от SDMX/PX-Web, у US Census нет пакета
с собственным тест-сьютом, который можно взять за источник истины —

Живые попытки из песочницы подтвердили точные URL для обоих: `ustat catalog

### Фаза 7 — готово

`core/query_plan.py`: `QuestionInterpretation` (то, что предлагает
planner — концепты, географии, периоды, трансформации, вид сравнения,
output_type, assumptions, needs_clarification) и `QueryPlan` (то же плюс
реальные кандидаты индикаторов из каталога). **Защита от галлюцинаций —
структурная, не промпт-инструкция**: в `QuestionInterpretation` физически
нет поля под код индикатора — planner может предложить только
natural-language `concepts`. `build_query_plan()` — единственное место,
где создаются `CandidateIndicator`, и делает это вызовом
`QueryEngine.search_indicator()` (тот же детерминированный поиск, что у
всех интерфейсов) — LLM в принципе некуда подставить выдуманный код.

Новый пакет `planning/` (параллельно `providers/`, изолирован, потому что
зависит от опционального внешнего LLM-клиента — секция 22):
- `planning/base.py`: `LLMPlanner`, структурный `Protocol` (тот же приём,
  что `MetadataDiscoverable`).
- `planning/rule_based_planner.py`: `RuleBasedPlanner` — без LLM и внешних
  зависимостей, вся фраза = один буквальный поисковый концепт, честно
  объясняет ограничение через `assumptions`, а не делает вид, что понял
  естественный язык.
- `planning/anthropic_planner.py`: `AnthropicPlanner` — Claude через
  **принудительный tool call** (`tool_choice={"type": "tool", "name":
  "propose_query_plan"}`, реальный, проверенный параметр Anthropic SDK), не
  свободный текст — модель может ответить только заполнив схему плана, где
  просто нет места под число или код. Системный промпт — прямое отражение
  секции 11 (ambiguity handling): типовая интерпретация при уверенности,
  явно записана в `assumptions`, `needs_clarification` только когда
  интерпретации дали бы существенно разный результат. Тот же паттерн, что
  `chat.py` — клиент инжектится, тестируется фейковым клиентом на реальных
  `anthropic.types` объектах, без ключа.

Выставлено уже сейчас, до полного `/ask` (Фаза 11): `ustat plan
"<question>"` (`--llm` для `AnthropicPlanner`) — план можно посмотреть до
того, как появятся вычисления/валидация (Фаза 9) или answer builder
(Фаза 11), по букве требования "expose query plans in developer/debug
mode". Живой прогон на реальном каталоге: `ustat plan "population"` нашёл
`SP_POP_TOTL`; `ustat plan "population of Afghanistan"` честно вернул
пустой список кандидатов — реальное, ожидаемое ограничение
rule-based planner'а, не баг.

`QueryPlan.selected_indicators` (Фаза 8) и `.validation_notes` (Фаза 9) —
уже в датаклассе, пустые: форма задана самим ТЗ (секция 10), стабилизация
сейчас избавляет от breaking change в вызывающем коде позже.

**146 офлайн-тестов** (было 133).

### Фаза 8 — готово

`core/selection.py::select_indicators(plan)` выбирает ровно одного
кандидата на концепт из `QueryPlan.candidate_indicators`, детерминированно
и объяснимо (секция 12), заполняя `QueryPlan.selected_indicators`. Чисто
функционально — без движка/сети: к моменту, когда план сюда попадает,
`CandidateIndicator` уже несёт метаданные каталога (`unit`/`frequency`/
`geographic_coverage`) — расширено именно в этой фазе, потому что это ровно
то, что `engine.search_indicator()` уже возвращал в `build_query_plan()`,
просто раньше не сохранялось.

Критерии скоринга (каждый — с явной человекочитаемой причиной, не только
числом): совпадение имени (точное вхождение концепта в название весит
больше, чем просто FTS-совпадение), географическое покрытие
(запрошенные регионы все покрыты > частично покрыты > не покрыты;
**неизвестное покрытие — нейтрально, не штраф**, важное отличие "не знаю"
от "точно нет"), совпадение частоты. Freshness/completeness (тоже из
секции 12) сознательно НЕ скорятся здесь — для них нужны реально
полученные наблюдения, а не только метаданные каталога — это задача
валидационного слоя (Фаза 9), не селекции.

**"Никогда не смешивать несовместимые ряды молча" (секция 12) — следствие
конструкции, а не отдельная проверка**: селекция всегда выбирает ровно один
источник на концепт (кандидаты одного концепта никогда не объединяются), и
если селекции разных концептов одного плана разошлись по разным
источникам — это явно добавляется в `assumptions`, а не остаётся неявным
до момента, пока кто-то не попробует их объединить.

Подключено в `tools.build_plan()` (и значит в `ustat plan`) сразу после
`build_query_plan()` — живой прогон на реальном каталоге показывает всю
цепочку: catalog match → причина выбора → `selected_indicators`.
**155 офлайн-тестов** (было 146).

### Фаза 9 — готово

**Вычисления**: `ComparisonColumn` получил `formula`/`input_series` —
именно то, что предыдущая оценка по UOSA-Bench назвала главным приоритетом
(`docs/benchmarks/uosa-bench-v1-assessment.md`). Каждая производная
колонка — старая (`with_growth`/`with_ratio`/`with_rank`) и новая — теперь
несёт оба поля. Новые операции, каждая протестирована отдельно:
`with_absolute_change`, `with_pp_change` (тот же расчёт, что abs_change,
но отдельный ключ/label — самодокументирующийся смысл), `with_cagr` и
`with_cumulative_growth` (одно значение на весь диапазон, записано в
конечном периоде; обе отклоняют неаннуальные периоды явной ошибкой, а не
молча считают неверный "годовой" темп по месячным данным), `with_index`
(ребейзинг к 100), `with_moving_average`, `with_difference` (разность
двух произвольных колонок), `with_share`/`with_per_capita` (тонкие,
явно названные обёртки над той же механикой, что `with_ratio` —
разделены, потому что это разные, часто запрашиваемые понятия по секции
14), `with_sum`/`with_average`/`with_weighted_average` (агрегация по
колонкам за период, веса — только явно заданные вызывающим, никогда не
выведенные; период пропускается, а не досчитывается частично, если
какой-то колонки не хватает). Новый `with_period_over_period_growth` —
та же математика, что `with_growth`, но под честным,
frequency-нейтральным именем — не переименовывал сам `with_growth`
(слишком много существующих вызывающих завязано на ключ
`__yoy_growth_pct`), просто дал альтернативу.

`SeriesResult` получил поле `unit` (второй пункт из той же оценки),
`ComparisonColumn` — `unit`/`frequency`, заполняются из реально
полученного `SeriesResult` в `compare_across_countries`/
`compare_across_indicators`. Честно: ни один провайдер пока не извлекает
`unit` из ответа источника (в отличие от frequency) — поле существует,
чтобы валидации было что читать, и чтобы будущему провайдеру, который
это умеет, не понадобилась ещё одна правка модели.

**Валидация**: `core/validation.py` — `validate_series()` (на сыром
`SeriesResult`, до сведения в таблицу: дубликаты периодов — WARNING, NaN
вместо None — FAIL, пустой результат — WARNING) и `validate_table()` (на
`ComparisonTable`: цитирование обязательно для базовых колонок — FAIL без
атрибуции; unit/frequency-согласованность — WARNING, и только когда ОБА
значения известны и расходятся, неизвестное не считается противоречием,
тот же принцип, что уже в `core/selection.py`; покрытие запрошенных
регионов/периода — WARNING; пробелы в годовом покрытии — WARNING,
консервативно только для колонок, чьи периоды все — 4-значные годы;
целостность lineage производных колонок — FAIL, если `input_series`
ссылается на несуществующую колонку). "Impossible transformations" из
секции 16 перехватываются раньше, структурно — самими функциями
трансформации (`ValueError` на неизвестный baseline/период/колонку), а не
дублируются здесь.

Живой прогон подтвердил: `with_growth` + `validate_table(...,
requested_geographies=("AFG","USA"), requested_start_period="2010")` на
реальных данных нашёл ровно то, что должен — отсутствующий запрошенный
регион и настоящий пробел в годовом покрытии, оба поимённо, не
проглочены молча. **193 офлайн-теста** (было 155).

### Фаза 10 — готово

`core/provenance.py::resolve_provenance(table, column_key, period)` строит
полную, прослеживаемую цепочку от любой ячейки `ComparisonTable` (базовой
или производной, на любой глубине) — `ObservationProvenance` для напрямую
полученного значения (провайдер, организация, датасет, id
индикатора/серии, география, период, значение, unit, официальный URL,
время получения) или `DerivedProvenance` для вычисленного (formula,
"Calculated by Universal Statistician", время расчёта, провенанс каждого
входа — рекурсивно). Живой прогон воспроизвёл пример из секции 17
почти дословно: провенанс ratio несёт формулу и резолвится в оба входа до
реальных наблюдений `WB_WDI`/`NY_GDP_PCAP_CD` с источником, датасетом и
временем получения.

Два небольших, обоснованных расширения модели сделали это возможным:
`ComparisonColumn` получил явные `indicator_id`/`ref_area` (раньше это
было неявно зашито в `key`, который означает РАЗНОЕ в зависимости от формы
сравнения — ref_area в `compare_across_countries`, indicator_id в
`compare_across_indicators` — без этого провенанс не мог назвать оба, как
в примере секции 17: "NY.GDP.PCAP.CD" + "Azerbaijan"); рекурсия работает
на любую глубину — rank-от-ratio или разность двух ratio (реально
достижимо через произвольные аргументы `with_difference`) резолвятся до
самых первичных наблюдений, не только на один уровень.

**Честно зафиксированный предел, прямо в докстринге резолвера, а не
спрятан**: `input_series` (Фаза 9) фиксирует, ИЗ КАКИХ КОЛОНОК получено
производное значение, но не из каких ИМЕННО ПЕРИОДОВ этих колонок — точно
для одно-периодных операций (ratio, share, per_capita, difference, index,
rank, sum, average, weighted_average), но реально неоднозначно для
операций, зависящих от нескольких периодов ОДНОГО И ТОГО ЖЕ входа
(`with_growth` — предыдущий+текущий, `with_cagr` — начало+конец, moving
average — всё окно). Для них резолвер не гадает единственный период —
прикладывает провенанс по КАЖДОМУ периоду, где у входа есть значение, с
явным `note`, объясняющим почему, вместо правдоподобно выглядящей, но
потенциально неверной точной ссылки на период.

**200 офлайн-тестов** (было 193).

### Фаза 11 — готово

`core/answer.py`: `AskResult` (question/query_plan/answer/table/chart/
sources/provenance/warnings/validation — ровно набор секций 18/20/21) и
`ChartSpec` (chart_type/title/axes/series/source_note — только данные, без
рендеринга; дашборд, Фаза 12, отрисует их уже имеющимся `recharts`).

`core/ask.py::answer_question(engine, question, planner=None)` — полностью
собранный пайплайн из целевой диаграммы секции 9: interpret → plan →
select → **retrieve** → **transform** → **validate** → **answer + chart +
citations**. Каждый шаг — переиспользование уже готового модуля, этот файл
добавляет только склейку:

- **Ретрив**: на каждую пару (выбранный индикатор × запрошенная
  география) — `QueryEngine.get_series()`, сборка в `ComparisonTable` через
  `build_comparison()`; именование колонок повторяет уже существующие
  конвенции `compare_across_countries`/`compare_across_indicators`, когда
  варьируется одна ось, и комбинирует оба, когда варьируются обе. Отказ по
  одной паре — предупреждение, не падение всей таблицы.
- **Трансформации**: `plan.transformations` (свободный текст от planner'а)
  диспетчеризуются по имени на функции `compose.py`, не требующие
  дополнительных аргументов (`growth`, `period_over_period_growth`,
  `absolute_change`, `pp_change`, `rank`, `cagr`, `cumulative_growth`).
  Трансформации, которым нужна явная колонка/веса (ratio, share,
  per_capita, difference, index, sum, average, weighted_average) НЕ
  диспетчеризуются автоматически — честно ограниченный охват первой
  версии, отмечен предупреждением, а не проигнорирован молча; остаются
  напрямую вызываемыми из `compose.py`.
- **Валидация**: `validate_table()` с запрошенными географиями/периодом
  из самого плана — валидация реально привязана к тому, что спросили, а
  не только к тому, что вернулось.
- **Текст ответа собирается шаблоном только из провалидированной
  таблицы** — никогда LLM не переписывает числа (секция 18): по строке на
  колонку с последним доступным периодом и значением, плюс дословно
  добавленные не-PASS находки валидации. Планировщик (даже LLM-based)
  участвует только в ИНТЕРПРЕТАЦИИ, до появления любых чисел.
- **Provenance**: `resolve_provenance()` (Фаза 10) — для последнего периода
  каждой колонки.
- Три исхода обрываются до ретрива явно, не общей ошибкой:
  `needs_clarification` (возвращает уточняющий вопрос, ретрив не
  запускается), география не определена, ни один кандидат каталога не
  выбран — по букве секции 23 ("если статистика не найдена — сказать
  прямо").

Выставлено на всех трёх интерфейсах: `POST /ask`/`POST /plan` (api.py,
`{"question": ..., "use_llm": false}` — `use_llm` включает
`AnthropicPlanner` через `ANTHROPIC_API_KEY` **сервера**, никогда не из
тела запроса; отсутствие ключа — чистый `400`, не падение), `ustat
ask`/`ustat plan --llm` (cli.py, общий хелпер `_resolve_llm_planner`), и
MCP-инструмент `ask` (сознательно только `RuleBasedPlanner` — у
MCP-подключённого хоста уже есть понимание естественного языка per
докстринг `mcp_server.py`, второй внутренний LLM-вызов был бы избыточен).

Живые прогоны подтвердили все три поверхности: `ustat ask population`
резолвит реальный кандидат каталога; `POST /ask {"question":
"population"}` по-настоящему через HTTP возвращает 200 с полной
структурой (и честно репортит отсутствие географии — rule-based planner
её не извлекает); `POST /ask {"use_llm": true}` без ключа сервера —
чистый `400`. **215 офлайн-тестов** (было 200 после Фазы 10).

Следующая фаза — Фаза 13, бенчмарки и укрепление.
