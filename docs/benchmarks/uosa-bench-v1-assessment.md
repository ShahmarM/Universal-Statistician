# UOSA-Bench v1.0 — оценка Universal Statistician

Оценка продукта (ветка `claude/universal-stats-assistant-fhr8bl`, коммит на
момент оценки — см. `git log -1`) по внешнему бенчмарку `UOSA-Bench v1.0`,
присланному пользователем. Дата: 2026-08-08.

## 0. Как читать этот документ

Дословное исполнение бенчмарка здесь невозможно, и это надо сказать прямо, а
не изобразить видимость соответствия:

- **Сеть заблокирована.** Egress-политика этой среды разработки блокирует
  любой внешний хост, кроме pypi/npm/github/anthropic (установлено и
  задокументировано ранее — см. `plan.md`, разделы про OECD и Росстат/ЕМИСС).
  Значит ни один живой запрос к `api.worldbank.org`, `data.imf.org`,
  `ec.europa.eu`, `statistikdatabasen.scb.se` не пройдёт. Блоки B/C/E/F/G
  бенчмарка, требующие retrieval и numerical accuracy против golden values
  из реальных источников, **технически невозможно исполнить в этой среде**.
- **Нет ключа Anthropic API.** `ustat chat` не запускался вживую ни разу
  (см. `plan.md`, раздел 9d). Блоки D (NLU) и J (conversational workflow),
  задуманные бенчмарком как проверка LLM-в-контуре, не проверены с реальной
  моделью.
- **Каталог — 4 индикатора.** В `providers/catalog_seed.py` сконфигурировано
  и проверено сквозным путём ровно 4 индикатора (по одному на WB_WDI,
  IMF_DATA_CPI, ESTAT_NAMA_10_GDP, SCB_TAB6471), а не 20 стран × 15 тематик,
  которых требует раздел 4 бенчмарка. OECD и Росстат/ЕМИСС осознанно не
  добавлены (см. `plan.md`).
- **Продукт — не conversational AI сам по себе.** По архитектурному решению
  (см. `plan.md`, раздел 2, «Чего избегать») этот проект не строит
  собственный NLU — понимание естественного языка делегируется LLM-хосту,
  подключённому через MCP/чат. Значит блоки D и J оценивают не наш код
  напрямую, а связку "наш инструментарий + любая LLM, которая его вызывает".

Вместо выдуманных баллов по 1000-балльной шкале — честная классификация
каждого блока/gate по фактическому коду, с конкретными ссылками на файлы и
строки, плюс то, что реально прогнано (offline pytest-сьют, 85 тестов, и
точечные smoke-проверки через `ustat`/`tools.py` — команды и вывод приведены
там, где это даёт значимое доказательство).

Легенда:

| Метка | Значение |
|---|---|
| ✅ | Поддержано архитектурой, с конкретным механизмом/тестом |
| ⚠️ | Частично — что есть и чего не хватает |
| ❌ | Не реализовано |
| 🚫 | Нельзя проверить в этой среде (сеть/ключ) — что именно проверить и как |

## 1. Gate criteria — самое важное в бенчмарке

Правило бенчмарка: любой провал gate = FAIL независимо от суммы баллов.

### GATE-01 — Fabricated data

**✅ Пройден по конструкции.** Ни один провайдер (`sdmx_provider.py`,
`pxweb_provider.py`) не имеет пути кода, возвращающего значение при сбое
получения данных — только исключение. Подтверждено `grep` по всему `src/`
на `interpolat|extrapolat|forecast|estimat` — **0 совпадений**. Живая
проверка:

```
$ ustat source NOPE
Unknown source 'NOPE'; known sources: ['ESTAT_NAMA_10_GDP', 'IMF_DATA_CPI', 'SCB_TAB6471', 'WB_WDI']
exit: 1
```

Ни разу не возвращён и не может быть возвращён fallback/дефолтный ряд под
видом официального. Не проверено на живом сетевом сбое конкретно (сеть
заблокирована), но `api.py::_call` уже ловит любые исключения провайдера
(включая сетевые) в HTTP 502 с текстом ошибки, а не подменяет пустым/нулевым
значением — см. `README.md`, раздел про CORS/502-баг из раунда 9b.

### GATE-02 — False official attribution

**✅ Пройден по конструкции.** `Attribution.source_id`/`source_name`
заполняются исключительно из `SDMXSourceConfig`/`PXWebSourceConfig` —
статических, явно зарегистрированных структур (`providers/registry.py`,
`providers/pxweb_registry.py`). Нет ни одного пути кода, который мог бы
подставить произвольную строку (например, из пользовательского ввода) в
поле `source_name`. Если LLM-хост вызовет `describe_source` с выдуманным
`source_id`, вернётся `UnknownSourceError` — не выдуманная атрибуция.

### GATE-03 — Irreproducible derived statistic

**⚠️ Частично.** Проверено на реальном выводе `tools.compare` (не выдумано —
запущено сейчас, фейковый провайдер, реальный код):

```json
{
  "key": "AFG__yoy_growth_pct",
  "label": "AFG: YoY growth %",
  "derived": true,
  "attribution": null
}
```

Что есть:
- Каждая базовая колонка несёт полную `Attribution` (источник, dataset_id,
  время получения, ссылка).
- Каждая производная колонка явно помечена `"derived": true,
  "attribution": null` — невозможно спутать с официальным значением
  (структурно, не только по докстрингу).
- Период и единицы (в смысле "то же измерение, что у входного ряда")
  сохраняются неявно — таблица строится на той же оси периодов, что и
  входные ряды.

Чего не хватает для полного прохождения GATE-03 (см. бенчмарк: "показать
исходные ряды; источник каждого ряда; формулу; период; единицы;
преобразования"):
- **Нет структурированного поля `formula`.** Есть только человекочитаемый
  `label` ("AFG: YoY growth %"), не машиночитаемая формула
  (`(curr - prev) / prev * 100`).
- **Нет структурированного поля `input_series`.** Связь производной колонки
  с исходной кодируется только в строке `key`
  (`AFG__yoy_growth_pct` → подразумевает `AFG`), а не явным списком.
- **Нет поля `unit`** нигде в `core/models.py` (проверено — ни у
  `Observation`, ни у `SeriesResult`, ни у `Attribution` такого поля нет).
  См. также F05/F06 ниже.

Итог: **воспроизвести можно** (все входные вызовы `get_series` с полной
атрибуцией доступны и детерминированы), но **calculation tree** в смысле
раздела H03 бенчмарка (`Derived series ↳ Non-oil GDP ↳ Employment ↳ formula
↳ result`) как отдельная машиночитаемая структура — не реализован.

### GATE-04 — Silent incompatible-series combination

**✅ Пройден по конструкции, для текущего API.** `compare_across_countries` и
`compare_across_indicators` (`core/compose.py:82-121`) принимают **один**
`source_id` на весь вызов — физически нельзя одним вызовом `compare()`
смешать номинальный ВВП из одного источника с реальным индексом занятости
из другого: сигнатура функции этого не позволяет.

**⚠️ Но не полная защита.** Внутри одного источника ничего не проверяет
совместимость единиц/определений между сравниваемыми `indicator_id` в
режиме "межиндикаторное сравнение" — например, `compare_across_indicators`
не остановит сравнение `B1GQ` (ВВП, млн EUR) с гипотетическим индикатором в
процентах в одной таблице. Явной проверки единиц измерения нет, потому что
поля `unit` не существует (см. GATE-03).

### GATE-05 — Silent methodology break

**❌ Не реализовано.** Grep по `src/` не находит никакой логики,
связанной с break-in-series/методологическими разрывами. `SeriesResult` не
несёт флага "before/after break". Источники (SDMX/PX-Web) в принципе могут
публиковать такую метаинформацию в метаданных (например, SDMX
`ObservationStatus`/`ANNOTATION`), но наш код её не читает и не
прокидывает. Если бы такой разрыв существовал в реальном ряду, система
молча склеила бы весь ряд как единый — **это реальный, непроверенный риск**,
а не просто "нет функции".

### GATE-06 — Hidden estimation

**✅ Пройден, сильнее всего в этом наборе gate.** `grep -ri
"interpolat|extrapolat|forecast|estimat" src/` → **0 файлов**. Единственные
арифметические операции над данными — `with_growth`/`with_ratio`/`with_rank`
в `core/compose.py`, все три — детерминированная арифметика над уже
полученными значениями, пропускающая `None` как `None`
(`test_to_series_result_handles_missing_values`,
`test_with_rank_skips_missing_values`). Отсутствующее значение никогда не
становится оценённым/интерполированным.

### GATE-07 — Wrong calculation

**⚠️ Корректно для того, что реализовано; многое из требуемого не
реализовано вовсе (см. блок E/Golden Derivation ниже).**

Проверено (юнит-тесты + повторный ручной прогон сейчас, реальный вывод см. в
GATE-03):
- `with_growth`: `(curr - prev) / prev * 100` — верная формула процентного
  изменения; рост-от-нуля корректно пропускается
  (`test_with_growth_skips_zero_baseline`).
- `with_ratio`: `value / baseline_value` — верно; неизвестная базовая
  колонка → `ValueError`, не тихий `0`/`None`
  (`test_with_ratio_unknown_baseline_raises`).
- `with_rank`: сортировка по убыванию, ранг 1 = наибольшее значение —
  корректно (`test_with_rank_orders_columns_by_value_descending`).

**Важный нюанс, не покрытый тестами до этой оценки:** `with_growth` всегда
называет колонку `yoy_growth_pct` и считает "предыдущий период относительно
текущего" в порядке сортировки строк периода — это **корректно только для
годовых рядов**. Для месячного ряда та же функция посчитает
month-over-month, но по-прежнему назовёт результат "YoY growth %" — **это
вводящее в заблуждение имя для нужд бенчмарка (E13 vs E14 разделены как
разные тесты, у нас это одна функция без различения частоты)**. Не FAIL по
арифметике (расчёт верен для того, что он на самом деле считает), но
маркировка вводит в заблуждение — стоит исправить.

CAGR (E06), percentage-point change (E19), moving average (E12), rolling sum
(E17), currency conversion (F04), index rebasing (E11), real/nominal
conversion через дефлятор (F01) — **не реализованы вовсе**, см. блок E (§2)
и Golden Derivation Suite (§4) — там, где функции нет, нельзя ни пройти, ни
провалить GATE-07 на ней, но и предъявить нечего.

**Вывод по gate:** ни одного случая **подтверждённой** фабрикации данных,
ложной атрибуции или скрытой оценки — три самых опасных gate (01/02/06)
проходятся по конструкции кода, не только "пока не тестировали". GATE-05
(методологические разрывы) — открытый, непроверенный риск при реальных

вердикт — FAIL**, поскольку GATE-05 не может быть подтверждён как пройденный
(нет механизма) и GATE-03/07 проходятся лишь частично. Это не то же самое,
что "система один раз сфабриковала данные" — источник FAIL здесь в
отсутствующих механизмах защиты, а не в зафиксированном инциденте.

### D. Natural language understanding (80)

🚫 **По архитектурному решению не наш код проверяет это напрямую** —
понимание языка делегировано LLM-хосту (MCP/чат), не встроенному NLU (см.
`plan.md`, «Чего избегать», п.1). Наш код предоставляет **структурированный
контракт**, на который LLM должен полагаться:

- `search_indicator` — точка входа для "как это называется в базе", вместо
  того чтобы LLM угадывал коды индикаторов.
- Каждый `get_series`/`compare` требует явных `source_id`/`indicator_id`,
  так что LLM обязан либо найти их через `search_indicator`, либо получить
  `UnknownSourceError`/`ValueError` — не может тихо подставить
  правдоподобный, но неверный код.

D05 (multilingual equivalence) — ✅ частично проверено: `Catalog` уже
проиндексирован на нескольких языках вручную для существующих 4 индикаторов
(`catalog_seed.py` — английский, французский, немецкий для ESTAT), и поиск
по любому из них находит один и тот же индикатор
(`test_search_is_multilingual`). Но это заслуга ручной multi-language
разметки в seed-данных, не автоматического NLU.

D01–D04, D06 (интерпретация вопроса, typo robustness) — 🚫 требуют реальной
LLM в контуре, не проверено (нет ключа).

### E. Derived statistics (190) — см. подробный разбор в §4 (Golden Derivation Suite) ниже

Кратко: **share/ratio (E01, E20) и per-capita/per-employee через ratio (E02,
E03) механически достижимы** через `with_ratio` при межиндикаторном
сравнении. **Growth (E05, частично) и rank реализованы.** Все остальные
20+ операций (CAGR, cumulative growth, moving average, rolling sum,
contribution to growth, index rebasing, currency conversion, YoY/MoM/QoQ как
различные операции, percentage-point change, weighted average, real/nominal
conversion, composite indicator workflow, dimension-mismatch detection,
stock-flow distinction) — **не реализованы**. Подробная таблица — §4.

## 5. Source Purity Score / Derived Data Trust Score / Confidence Status

- **SPS (Source Purity Score).** По конструкции = 100% для всего, что
  вообще возвращается: `Provider` не имеет пути получения значения не из
  зарегистрированного официального источника. Не измерено эмпирически на
  реальном трафике (сеть заблокирована), но гарантировано архитектурой, а не
  дисциплиной промптинга.
- **DDS (Derived Data Trust Score, §20).** Разбор по компонентам для текущих
  derived-колонок (`with_growth`/`with_ratio`/`with_rank`):

  | Компонент | Балл из | Есть? |
  |---|---|---|
  | Все input series официальные | 20 | ✅ (структурно гарантировано) |
  | Правильная формула | 20 | ✅ (проверено юнит-тестами, GATE-07) |
  | Единицы совместимы | 15 | ❌ нет проверки — потому что нет поля `unit` |
  | Периоды совместимы | 10 | ✅ (общая ось периодов, `build_comparison`) |
  | География совместима | 10 | ⚠️ гарантировано только для cross-country (одна и та же переменная `ref_area` как ключ), не проверяется для cross-indicator |
  | Frequency корректна | 10 | ❌ не проверяется (см. C04) |
  | Полная provenance | 10 | ⚠️ частично (см. блок H) |
  | Результат воспроизводим | 5 | ✅ |

  **Оценка: ~65–70 из 100** для текущих derived-рядов — ниже порога **≥95**,
  необходимого бенчмарком для статуса "Verified Derived Statistic".
- **Confidence Status (§21).** Ни один из шести статусов
  (🟢Official/🟢Verified Derived/🔵Methodology-derived/🟣User-defined/
  🟠Estimated/🔴Not available) не реализован как явное поле ни в одном
  API-ответе. Ближайшее — булев `derived` в `ComparisonColumn`. Это
  однозначный, легко устранимый пробел (см. рекомендации).

## 7. Итоговая классификация (раздел 24)

Дать формальный балл по 1000-очковой шкале было бы нечестно — большая часть
блоков (B численно, D, F, G, часть I/J) не может быть содержательно
измерена в этой среде, и присваивать баллы "на глаз" противоречило бы духу
самого бенчмарка (раздел 27: "может ли независимый аналитик воспроизвести
каждую цифру"). Вместо балла — качественная классификация по тем же шести
уровням:

**Оценка: ниже 700 — "Search/Chat Prototype" по формулировке бенчмарка сам
по себе неточен для описания того, что реально построено** (это не
поисковый прототип — есть настоящая архитектура с provenance, детерминизмом,
кэшем, воспроизводимостью), но по критериям, которые бенчмарк использует для
более высоких классов, продукт им не соответствует:

- **Не Reference-grade / Production-grade / Professional Beta (700+):**
  отсутствует весь блок G (revisions/vintage/конфликты), нет Confidence
  Status, нет `unit`/`formula`/`input_series` в provenance, 15/20 операций
  Golden Derivation Suite отсутствуют, нет экспорта в форматы кроме JSON,
  gate GATE-05 не может быть подтверждён как пройденный.
- **Сильнее, чем "просто чат-обёртка над API":** GATE-01/02/06 проходятся
  **по конструкции кода**, не по обещанию промпта — отсутствие фабрикации,
  ложной атрибуции и скрытых оценок гарантировано архитектурой
  (`Provider`/`Attribution`/отсутствие estimation-кода), что бенчмарк явно
  считает необходимым, но не достаточным условием для высокого класса.

**Итог: продукт — надёжный, честно спроектированный fundamentals layer
(data access + provenance + derived tables + 5 интерфейсов), но не
"доверенный статистический помощник" в полном смысле бенчмарка. Ближе всего
к нижней границе "Consumer-grade Assistant", вероятно ниже её из-за
отсутствия блока G и Confidence Status целиком.**

## 8. Приоритизированные рекомендации

По убыванию отношения "польза для прохождения бенчмарка / стоимость
реализации", в рамках уже существующей архитектуры:

1. **Добавить `unit` в `Observation`/`SeriesResult` и `formula`/
   `input_series` в `ComparisonColumn`.** Дешёвая правка модели данных
   (`core/models.py`, `core/compose.py`) — напрямую закрывает GATE-03 полностью,
   поднимает DDS с ~65–70 до потенциально 95+, закрывает F05/F06 частично.
2. **Явный `status`-таксономия** (Official/Derived/Composite/User-defined/
   Estimated) вместо булева `derived` — прямое попадание в §21 Confidence
   Status, минимальные изменения (`ComparisonColumn`, `SeriesResult`).
3. **Прокинуть `frequency` в `ComparisonTable`/`build_comparison`** и
   предупреждать при смешении частот — закрывает C04, часть DDS
   ("Frequency корректна").
4. **Переименовать/разделить `with_growth`** на явные `with_yoy_growth` /
   `with_period_over_period_growth`, чтобы не называть месячный расчёт
   "YoY" — прямое исправление находки по GATE-07.
5. **Percentage-point change как отдельная функция** (`with_pp_change`) —
   явно требуется E19, дёшево (пара строк по образцу `with_growth`).
6. Дальше по стоимости/пользе — уже не "дешёвые правки", а новые
   возможности: расширение каталога за пределы 4 индикаторов, обнаружение
   конфликта источников (нужен минимум 2 источника на индикатор), vintage-
   хранилище (нужна собственная БД версий, а не просто TTL-кэш),
   currency conversion (нужен ещё один провайдер — FX rates), CAGR/moving
   average/rolling sum/index rebasing (несложные новые функции в
   `compose.py`, по образцу уже существующих трёх).
